02 — Case studies

Engineering case studies

Client work doesn't become a public repo. These are the decisions, written as ADRs: context, decision and outcome. Clients identified by sector only.

ADR-01

From timeouts to 2.5 s in receivables anticipation

GFT Brazil · 2023–2024Banking sector · solutions consulting
RedisMySQLAPI GatewayPerformance
Context

The corporate receivables-anticipation system was blowing past the API Gateway timeout: over 12 seconds per request on large batches of payment slips.

Decision

I traced the bottleneck to relational persistence and replaced MySQL with a Redis caching layer for simulation data, with a 24-hour TTL.

Outcome2.5 s

maximum per request. Batches of up to 2,000 concurrent payment slips, zero timeouts and 100% of transactions completed.

ADR-02

Java 25 and Spring Boot 4.1.1 migration with AI agents

GFT Brazil · 2026–presentBanking sector · account opening
Java 25Spring Boot 4.1.1OpenRewriteMongoDBClaude agents
Context

A bank's account-opening services had to move to new versions without compromising security or architectural consistency.

Decision

I broke the scope into tasks with clear contracts (SDD). Claude agents and OpenRewrite generate the code; I review it critically and gate what reaches the main branch.

Outcome8 of 16

services in scope migrated by me; the rest reviewed and merged under the same main-branch gate.

ADR-03

Anti-fraud in .NET with hexagonal architecture

Officecom · 2024–2026Sports betting sector · regulation
.NETC#HexagonalCode review
Context

A mission-critical personal-data validation and anti-fraud service, required by Brazil's new sports-betting regulation.

Decision

A monolith in hexagonal architecture on .NET, keeping the domain isolated from integrations. I led 3 developers (1 mid-level, 2 juniors), owning scope breakdown and rigorous code review.

Outcome750/day

new users validated per day, plus 200 daily biometric re-validations.

ADR-04

From IBM CastIron to Kafka: near-real-time invoicing

GFT Brazil · 2021–2022Health insurance sector · GCP
KafkaKSQLJava 15GCPSalesforce
Context

Customer invoice generation relied on batch routines over a legacy middleware (IBM CastIron) with high licensing costs.

Decision

I moved the integration to an event-driven architecture with Apache Kafka and KSQL. A Java 15 Kafka consumer fetches data asynchronously, enriches it through internal APIs and sends it to Salesforce.

OutcomeBatch → events

Invoices generated in near real time instead of batch runs, and IBM CastIron licensing costs eliminated.
